## 1. 分类是怎么判的

分类词表在 `data/taxonomy.json`。改那个文件就能改结果，不用碰 Python。

判定分四步，顺序固定：

**第一步：强词。** 强词是不会有歧义的词（`kubernetes`、`小红书`、`装修`、`etf`）。
标题命中权重 ×3，摘要命中 ×1。摘要里的 URL 会先被剥掉——不然「译文地址:http://…」
这种文本会把条目拽到错误的桶里。

**第二步：弱词。** 弱词是泛用词（`工作流`、`管理`、`工具`、`学习`）。它们只在两种情况下
起作用：给强词同分的类目打破平局；或者一个类目只有弱命中但分数过了门槛（≥3）。
一个类目只有弱命中且没过门槛，算未分类。

**第三步：同来源继承。** 没有任何信号的条目，继承**同一个来源**的主导类目。
这里有个重要的修正：继承只在 **±2 年的时间窗口**内生效。收藏来源本身常常是主题专栏，
但同一个来源可能横跨很多年——2014 年收藏的装修文章如果继承 2025 年的「自媒体与商业变现」，
结果就是错的。

**第四步：人工判定。** `overrides` 表，key 是收藏条目的 id，value 是 `[类目, 理由]`。
理由会保留在文件里，方便日后复核。

还有一层**栏目启发式**（`columns`）：判断这条收藏天然属于哪种编辑角度——
亲历 / 反常识 / 决策 / 热点。它和主题分类是两条独立的轴，一个类目里可能各种栏目都有。

### 词表的小陷阱

- **ASCII 词按词边界匹配。** `java` 不会命中 `javascript`，`ai` 不会命中 `email`。
  边界是「非 `[a-z0-9_]`」。CJK 不算边界，所以「AI老鸟」还能命中 `ai`。
- **中文词额外匹配去空格的副本。** 「web 应用」要能命中 `web`。
- **正则关键词用 `re:` 前缀。** 比如 `re:\d+\s*本` 匹配「读完 12 本」。
- **加权字段是每类目的**。`strong` 和 `weak` 各有一套 `{类目: {关键词: 权重}}`。

改完词表重跑 `wfc_capture.sh classify` 即可，不用清缓存。

## 2. 分层

主题分类回答「这是什么」，分层回答「值不值得抓」。

| 层 | 判定 | 说明 |
|---|---|---|
| T1 | 年份 ≥ 2024 | AI 时代的内容，默认抓这层 |
| T2 | 2024 年前，但类目属于受众关心的（管理 / 金融 / 理财 / 生活） | 按需 |
| T3 | 2024 年前的其余 | 旧技术细节 |
| IMG | 链接含 `image_detail` | 图片消息页，多半已失效 |
| NOLINK | 没有链接 | 图片收藏、聊天文件等 |

`T2` 的类目清单在 `taxonomy.json` 的 `tiers.T2.categories` 里。

### 层级在哪一步筛

`classify` 把**所有层**的 URL 都写进 `urls/<分类>.txt`，同时在 `urls/_index.json` 里记下
每个 URL 属于哪一层：

```json
{
  "https://mp.weixin.qq.com/s?__biz=...&mid=...&sn=...": {
    "category": "AI工作流与Agent", "tier": "T1",
    "title": "…", "timestamp": "2026-03-14T09:12:00"
  }
}
```

`scrape --tier T2` 是**逐条**从索引里挑出 T2 的那些。所以分类跑一次就够，换层不用重跑。

> 早先的实现是拿 `scrape --tier` 去比 `_manifest.json` 里记的那一个层级。后果是
> `classify --tier T1` 之后 `scrape --tier T2` 会静默返回 0 篇，看起来像「没有可抓的
> 内容」——实际上只是层级对不上。逐条过滤没有这个坑。

`classify` 每次运行会先清掉 `urls/` 下上一轮留下的 `.txt` 文件。旧清单留着会被当成
当前数据抓一遍。

## 3. 正文抓取

正文靠 `wechat-article-scraper` 抓。**微信文章页必须用真实浏览器打开**——微信加了
`poc_token` 校验，直接发 HTTP 请求会拿到一个 17KB 的「环境异常」验证页，把 token 拼进
URL 也没用，因为 token 是逐篇下发的。

正文的 HTML→Markdown 转换在浏览器里做完再落盘，不进模型上下文。一篇原始 HTML 几十到
几百 KB，转完的 markdown 只有十分之一。

输出落在 `<dataset>/articles/<分类>/`，文件名 `{发布日期}-{标题}.md`：

```markdown
---
title: "文章标题"
author: "作者"
url: "https://mp.weixin.qq.com/s?__biz=...&sn=..."
pub_date: "2026-07-31"
fetched: "2026-11-07T14:16:36+08:00"
source: "wechat-article-scraper"
tags:
  - wechat-favorites
---
```

## 4. 浏览器会话僵死

**这是抓不动的时候第一个要怀疑的东西。**

现象：批量跑到十几篇之后开始连续「浏览器打开失败」或「eval 超时」。但手动开同一个
URL 又能正常打开——所以不是 URL 的问题，也不是标签页堆积（`tab list` 始终只有 1 个）。
是 opencli 的浏览器会话整体僵死了。

处理：

1. **按 ≤6 篇分块跑**，每块之间让 scraper 停掉 daemon（它的默认行为就是抓完停）
2. `--delay 20`
3. `--window foreground`（默认值，遇到验证时更稳）
4. **只重试失败的那几篇**——用 `.index.json` 的 key 算出失败集（成功的都在里面）

**别整批重来。** 重抓已经成功的那些会撞上重名处理逻辑。

skill 默认已经按 1~3 配好了（`WX_FAV_CHUNK=6`、`WX_FAV_DELAY=20`），第 4 步由
`wfc_capture.sh scrape` 自动处理：每块跑完读 `.index.json`，把缺的那些记进回执的
`failed_items`。

### 不是微信文章链接的那些

收藏夹里不只有公众号文章，还有抖音视频页、头条、51CTO、各种资讯站。抓取器只处理
`mp.weixin.qq.com`，其它链接进了待抓清单也只会让每条空转三次重试、白等两分钟，然后
报一个看起来像「文章没了」的失败。

`classify` 把这类链接分流到 `urls/_skipped.json`，不写进待抓清单。`scrape` 的回执里
`skipped_not_wechat` 是它们的数量——**这不是失败，是本来就抓不了**，汇报时分开说。

### 重试的边界

`scrape` 会把失败的篇**重试一次**，再不行就如实报成失效。这个上限是刻意的：

- **会话僵死是可以重试的。** 失败的是「这一块」，不是「这些文章」——下一块是新会话，
  往往又好了。重抓已经成功的那些会撞上重名逻辑，所以只重试缺的。
- **原文不可见是重试不好的。** 删除 / 违规下架 / 隐私设置，重试一万次也一样。每篇只重试
  一次，省下的时间留给还救得回来的那些。

要关掉重试：`--no-retry`。

### 但「第一篇就全失败」是另一回事

会话僵死是跑到十几篇之后才出现的。**如果从第一篇就开始每篇都「浏览器打开失败」，
那不是僵死，是环境没起来。** 2026-11-07 实测踩到两个叠在一起的原因：

1. **daemon 没启动。** `opencli daemon status` 未运行时输出的是 `Daemon: not running`
   ——它里面含 "running" 字符串，早期的 `if "running" not in status` 判断会把没运行
   的 daemon 判成在运行，于是永远不 restart。已修 `wechat-article-scraper/scripts/scrape.py`。
   临时绕过：`opencli daemon restart` 再跑。
2. **session 租约是死的 + 没选 profile。** `opencli profile list` 显示有已连接的
   profile 但 `none selected`。`opencli browser <session> close` 释放死标签页，
   再 `opencli profile use <某个 profile>`。

判断方法：`opencli browser <session> eval "document.title"` 能出标题就说明浏览器活着。
先花十秒确认环境，再决定要不要重试。

### 失败的条目多半永远不会成功

三种情况重试一万次也一样：

- 原文被发布者删除
- 因违规无法查看
- 作者开了隐私设置

这些条目的**元数据还在收藏库里**（标题、来源、收藏时间），只是正文拿不到。
汇报时说「原文已不可见」，不要说「抓取失败」——前者是事实，后者会让人以为还有救。

## 5. 图片插件

抓下来的 Markdown 里图片是 `mmbiz.qpic.cn` 的原始 CDN 地址，**不下载**。这是刻意的：
正文图片体积远大于文字，下载既慢又把 vault 撑大。

但 vault 里可能有插件推翻这个设计。`obsidian-local-images-plus` 开着 `processCreated`
时，会在文件创建时把外链图片下载到 `assets/` 并把 markdown 图片语法改写成
`![[assets/xxx_MD5.webp]]`。

想保持「只留 URL」，要在它的设置里排除采集目录。三个条件缺一不可：

1. **`ExcludedFoldersList` 必须非空。** 只设 `ExcludedFoldersListRegexp` 等于没设——
   插件的实现要求两个条件同时满足。
2. **正则要前缀匹配。** 插件比对的是文件的父目录路径 `file.parent.path`，不是文件路径，
   所以要覆盖整个采集目录得用 `^raw/xxx/` 而不是精确匹配。插件 UI 生成的是精确匹配
   `(^路径$)`，只匹配目录本身。
3. **必须整库重载。** `obsidian plugin:reload` **不会**重新读 `data.json`——改完配置
   必须 `obsidian reload`（整库重载）才生效。实测 `plugin:reload` 之后磁盘上的配置是对的，
   但插件内存里还是旧值。

配置写在 `.obsidian/plugins/obsidian-local-images-plus/data.json`（改前先备份）。
**别在插件 UI 里编辑该项**，UI 会把它重置回精确匹配。

验证方法：在目标目录和对照目录各放一个含**真实** mmbiz 图片的 md，等 10 秒看是否被改写。
用假 URL 测不出来——下载失败时插件会原样保留，测不出区别。

## 6. 判重与状态文件

每个类目目录下三个文件：

| 文件 | 内容 | 用途 |
|---|---|---|
| `.index.json` | URL → `{file, title, pub_date, fetched, images, text_len}` | **判重的唯一依据** |
| `.state.json` | 按抓取顺序记录的 URL 列表 | 下次从哪继续 |
| `.crawl.log` | 每次运行的实时日志 | 排障 |

判重靠 URL，不靠文件名——同一篇文章的标题可能变，但 URL 不会。
